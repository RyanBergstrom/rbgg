### 3. Ready-to-Inject Instruction Patches

**Pre-Edit / Planning Rules**

```md
- For UI layout changes, inspect the existing CSS/component structure and use the browser tool before editing; do not guess dimensions, overflow, or z-index.
- For validator changes, run the targeted tests first and identify the failing invariant before editing.
- Change one concern per edit; do not batch unrelated CSS, validator, and test changes.
```

**Execution & Retry Circuit Breakers**

```md
- Stop after two failed attempts at the same hypothesis; switch to a minimal repro or targeted test instead of repeating edits.
- Do not create temporary debug scripts or leave debug logging; use existing tests and remove diagnostics after diagnosis.
- If a dev server must stay running, start it with the background process tool; do not run long-lived servers in the foreground.
```

**Definition of Done / Verification Gates**

```md
- Backend validator changes require the targeted FoF tests to pass: `pytest tests/test_fields_of_fire.py tests/test_fof_turn_sequence.py -q`.
- Frontend changes require `npm run check` and, for UI changes, browser validation of rendering, console, and network requests.
- Remove debug logging and temporary files before finishing.
- When changing legal-move invariants, add or update the test that proves the negative case.
```

### 4. Workflow & Mode Adjustments

- Use `Plan` mode for multi-file UI layout work (hover previews, stacking, overflow), then `Code` mode for the approved single-file edits.
- Use `Debug` mode for failing targeted tests; do not use `Code` mode to iterate blindly on test failures.
- Keep a fast verification pair available: `cd api && python -m pytest tests/test_fields_of_fire.py tests/test_fof_turn_sequence.py -q` and `cd web && npm run check`; run browser validation after any UI change.
